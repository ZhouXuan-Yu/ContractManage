# 通用合同管理系统外部系统集成边界与 Mock 方案

> 版本：V1.0
>
> 状态：合同系统内部适配契约设计，待外部系统提供正式接口后联调
>
> 原则：不替外部系统虚构 URL、字段和鉴权；先定义合同系统需要的业务能力、内部标准模型和 Mock 行为。

## 1. 集成总原则

```text
合同系统业务服务
    -> 内部标准接口 / Provider 接口
        -> 具体 Adapter
            -> 外部系统或 Mock
```

- 合同业务代码只依赖内部标准接口，不直接调用外部系统。
- 外部系统的 URL、鉴权、字段映射、错误码和状态映射只放在 Adapter 与配置中。
- 外部系统不可用时，合同保存和历史查询不能被阻断；需要外部结果的动作进入失败、待补偿或待人工处理状态。
- 外部返回的数据必须先完成格式校验、权限校验、版本校验和幂等校验，再写入合同系统。
- 所有外部调用记录调用方、业务对象、请求幂等键、外部流水号、结果摘要、耗时和失败原因；敏感内容不得写入普通日志。

## 2. 外部依赖边界

| 外部系统 | 外部系统负责 | 合同系统负责 | 一期开发方式 |
|---|---|---|---|
| HR/组织系统 | 员工、组织、岗位和 HR 数据范围 | 引用员工/组织 ID、展示快照和权限使用 | Mock，后续接真实接口 |
| 外部交易对方主数据系统 | 客户、供应商及其他外部主体主数据；可能是一个系统，也可能是多个系统 | 引用外部主体 ID、合同身份映射和关键时点快照 | Mock，后续按实际系统接入 |
| 我方主体/法人系统 | 我方公司、法人或组织主体主数据 | 保存我方主体外部 ID、名称快照和合同引用 | Mock，后续接真实接口 |
| 文件服务 | 文件上传、物理存储、预览、下载、短期链接、病毒扫描 | 附件关联、业务分类、版本、权限、审计和状态 | Mock 或测试环境 |
| 审批系统 | 流程、节点、审批人、审批页面和审批流转 | 发起、关联、状态同步、锁定、补偿和审计 | Mock |
| AI Provider | 模型调用、工作流执行、解析和审查推理 | 任务、版本绑定、Schema 校验、重试、人工确认、权限和审计 | Mock，后续可接 Dify 或其他 Provider |

通知、电子签署、归档借阅等系统属于后续能力：通知可通过主系统通知能力扩展，电子签署和归档借阅属于已确定的二期/三期范围，一期不把它们作为生产依赖，但在接口设计中预留扩展位置。

## 3. 主数据系统适配

### 3.1 合同系统需要的能力

```text
getEmployee(external_id)
searchEmployees(query, scope)
getOrganization(external_id)
searchCounterparties(query, scope)
getCounterparty(external_id)
listOurSubjects(scope)
getOurSubject(source_type, external_id)
```

合同系统统一把客户、供应商、合作方、咨询机构等定义为“交易对方”，只保存外部主体 ID、必要展示信息和关键时点快照，不复制外部主档案。客户、供应商和合作方不是合同系统里的不同主体模块，而是同一交易对方在具体合同中的不同业务关系。它们是否由一个或多个外部系统维护，属于外部主数据架构问题。

### 3.2 内部标准模型

```json
{
  "source_type": "customer",
  "external_id": "external-id",
  "subject_type": "organization",
  "subject_role": "customer",
  "subject_name": "展示名称",
  "organization_id": "external-org-id",
  "enabled": true,
  "fetched_at": "2026-08-27T10:00:00+08:00"
}
```

实际字段以外部系统提供的契约为准。合同系统不得把 `subject_name` 当作唯一关联依据。

### 3.3 外部系统需提供的信息

- 各自系统的主体类型和来源系统编码。
- 外部 ID 的稳定性和唯一性规则。
- HR 员工/组织接口、外部交易对方查询接口和我方主体接口；客户和供应商是否共用一套外部接口待确认。
- 组织、部门、负责人和数据范围接口（由 HR 或统一组织系统提供）。
- 主体停用、离职或归档后的查询规则。
- 敏感字段是否允许返回，以及脱敏要求。
- 接口鉴权、分页、限流、超时和错误码。

### 3.4 主数据集成规则

- 合同主体关联必须保存 `source_type + external_id`，不能只保存名称。
- 创建合同前校验主体当前是否存在、启用且允许签约；已停用主体不能用于新合同。
- 主体名称、组织或岗位变化不修改已经固化的历史合同快照。
- 同一外部主体可以在不同合同中承担客户、供应商、合作方等不同合同关系。
- 客户、供应商和员工的业务身份由合同记录表达，不在主数据系统之间互相复制。
- 外部主数据暂时不可用时，已保存合同和历史快照可查询；新建或关联操作进入待补偿，不伪造主体信息。

## 4. 文件服务适配

### 4.1 内部标准接口

```text
requestUpload(context) -> upload_ticket
confirmUpload(upload_ticket) -> file_ref
createAttachment(contract_context, file_ref, attachment_meta) -> attachment
getPreviewLink(attachment_id, purpose) -> temporary_link
getDownloadLink(attachment_id, purpose) -> temporary_link
archiveFile(file_ref, reason) -> result
deleteOrRevokeFile(file_ref, reason) -> result
```

### 4.2 关键约束

- 上传必须绑定业务对象、文件用途和操作者。
- 上传完成后必须校验 `file_id`、文件大小、文件哈希和文件状态。
- 合同系统先创建或确认附件关联，再允许文件出现在合同详情中。
- 预览和下载每次先校验合同权限，再申请短期链接。
- 数据库不保存文件二进制、物理绝对路径或长期公开 URL。
- 删除操作优先走文件服务归档或撤销；是否物理删除由保留策略决定。
- 原始文件、签署文件、模板文件、履行佐证、变更协议和导出文件必须区分业务分类。

### 4.3 外部系统需提供的信息

- 合同中心区对应的业务空间、租户或目录标识。
- 上传凭证机制和完成确认机制。
- `file_id`、哈希、大小、格式、扫描状态和对象状态字段。
- 预览、下载短期链接的有效期和权限模型。
- 文件删除、归档、恢复和保留策略。
- 病毒扫描、文件格式白名单、单文件和单合同容量限制。
- 断点续传、重复上传和幂等规则。

## 5. 审批系统适配

### 5.1 内部标准接口

```text
submitApproval(contract_snapshot, approval_config_snapshot, idempotency_key)
  -> approval_instance
queryApproval(approval_instance_id)
  -> approval_status
withdrawApproval(approval_instance_id, reason, idempotency_key)
  -> operation_result
forceTransfer(approval_instance_id, target_user_id, reason, idempotency_key)
  -> operation_result
receiveApprovalEvent(event_id, payload)
  -> sync_result
```

### 5.2 业务规则

- 提交审批时保存合同关键数据和审批配置快照。
- 审批中合同业务状态仍为草稿，`approval_status` 单独表示审批中。
- 审批中锁定主体、金额、正文、类型扩展字段和付款计划等关键数据。
- 审批通过进入待签署；驳回或撤回回到草稿并恢复编辑。
- 待签署撤回时，原审批实例作废，重新提交生成新的审批实例，历史记录不可覆盖。
- 外部回调按外部实例 ID、事件 ID和合同审批代次幂等；允许重复和乱序回调。
- 回调缺失时通过主动查询补偿；外部系统不可用时进入待同步或失败状态并支持人工处理。

### 5.3 外部系统需提供的信息

- 审批实例创建、查询、撤回和转交接口。
- 审批实例 ID、审批编号、业务单号和代次关联规则。
- 审批人、审批节点和审批历史返回格式。
- 回调地址、签名鉴权、事件 ID、事件时间和重试规则。
- 通过、驳回、撤回、转交、失效等状态定义。
- 审批实例作废和重新发起规则。
- 外部审批页面跳转地址或嵌入能力。

## 6. AI Provider 适配

### 6.1 内部标准接口

```text
submitExtract(task_context, idempotency_key) -> ai_task
submitReview(task_context, idempotency_key) -> ai_task
queryTask(provider_task_id) -> task_status
getTaskResult(provider_task_id) -> provider_result
cancelTask(provider_task_id) -> operation_result
testConnection(provider_config) -> connection_result
```

### 6.2 必须传递的上下文

```json
{
  "contract_id": "contract-id",
  "content_version_id": "content-version-id",
  "contract_type_id": "contract-type-id",
  "task_type": "extract",
  "review_view": "party_a",
  "schema_version": "v1",
  "content_hash": "sha256",
  "source_text": "合同正文或分段引用"
}
```

### 6.3 业务规则

- AI 解析和 AI 审查都必须绑定合同正文版本。
- `content_hash + schema_version + task_type` 作为重复任务判断依据。
- Provider 返回结果先经过 Schema 校验，失败不能伪装成低风险或空结果。
- 解析结果必须保存置信度、原文依据、缺失字段和来源版本。
- 审查结果必须保存风险等级、风险点、原文依据、理由、建议和置信度。
- AI 结果不能直接改变合同状态、审批结果或签署状态。
- 已人工确认的数据不得被后续 AI 任务直接覆盖；重新解析必须形成新结果版本。
- 失败、超时、Schema 错误和低置信度结果进入可见的待处理状态，支持人工重发和确认。
- AI Provider 可为 `mock`、`dify`、`direct_model` 或其他平台；页面和业务服务不感知具体 Provider。

### 6.4 外部 AI 平台需提供的信息

- 任务提交、查询、结果回收和取消能力。
- 同步、轮询或回调方式及其限制。
- Provider 任务 ID 和结果版本规则。
- 结构化输出约束、最大文本长度和分段建议。
- 工作流/模型版本标识。
- 鉴权、限流、超时、计费和错误码。
- 私有化部署、数据留存、日志脱敏和模型调用边界。

## 7. Mock 方案

### 7.1 Mock 原则

- Mock 使用与内部标准接口一致的请求和响应，不模拟某个外部厂商的私有字段。
- Mock 能主动制造成功、失败、超时、重复、乱序和数据不完整场景。
- Mock 数据固定、可重置、可按测试用例选择，不依赖真实外部网络。
- Mock 结果必须写入与真实 Adapter 相同的合同系统表和审计链路。

### 7.2 最小场景矩阵

| 依赖 | 正常场景 | 异常场景 |
|---|---|---|
| HR/组织 | 查询员工、组织和数据范围 | 不存在、已离职、停用、超时、字段缺失、无权限 |
| 外部交易对方主数据 | 查询客户、供应商及联系人 | 不存在、停用、不可签约、主体类型不匹配、超时、字段缺失、无权限 |
| 我方主体系统 | 查询法人/我方主体 | 不存在、停用、重复默认主体、超时、字段缺失 |
| 文件服务 | 上传确认、预览、下载、附件关联 | 哈希不一致、病毒失败、重复上传、链接过期、服务不可用 |
| 审批 | 提交、查询、通过、驳回、撤回、转交 | 重复回调、乱序回调、审批人离职、超时、查询补偿失败 |
| AI | 解析成功、审查成功、人工确认 | 超时、重试耗尽、Schema 错误、低置信度、旧版本结果返回 |

### 7.3 Mock 测试数据

- 至少准备劳动、采购、销售、服务、租赁和自定义合同样例。
- 每类合同准备正常、缺字段、风险条款、长文本和格式异常样例。
- 准备多轮审批、待签署撤回、作废、终止和变更补充协议样例。
- 所有主体、文件、审批实例和 AI 任务 ID 使用可追踪的固定测试 ID。

## 8. 商用联调门槛

外部系统提供正式接口后，逐项完成：

1. 字段、字典和 ID 映射确认。
2. 鉴权和密钥管理确认。
3. 超时、重试、限流和幂等确认。
4. 回调签名、事件 ID 和补偿机制确认。
5. 敏感数据、日志、留存和跨环境隔离确认。
6. 沙箱环境联调和故障演练。
7. 正常流程、重复请求、服务不可用和数据不一致测试。
8. 生产配置、监控、告警、审计和回滚方案确认。

在上述内容未确认前，一期可以继续使用 Mock 开发，但不能宣称已完成生产级外部集成。
