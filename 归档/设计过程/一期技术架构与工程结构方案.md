# 通用合同管理系统一期技术架构与工程结构方案

> 版本：V1.0
>
> 适用范围：一期可商用 MVP
>
> 开发原则：前端原型、后端业务和 Mock 适配并行，按业务闭环联调；不采用“前端全部完成后再开发后端”或“后端全部完成后再开发前端”的单线方式。

## 1. 架构目标

- 合同是唯一业务中心，客户、供应商、合作方和员工统一作为交易对方引用。
- 合同业务不直接依赖 HR、文件、审批或 AI 第三方返回结构。
- 一期先用 Mock 完成闭环，正式外部接口到位后只替换 Adapter。
- 所有关键操作经过后端权限、状态、版本、幂等和审计校验。
- AI、审批和文件处理采用异步任务，不阻塞合同草稿保存和历史查询。
- 数据库以 `D:\project\hr-contract\数据库表\合同管理.docx` 为权威设计。
- 为二期多组织、统计、电子签署和更多 AI 能力预留扩展点，但不提前实现二期业务。

## 2. 总体架构

```text
浏览器 Web
    -> 前端路由 / 权限展示 / 表单 / 详情页签
        -> 合同系统 API
            -> 认证与权限层
            -> 合同领域服务
            -> 模板与正文版本服务
            -> 交易对方引用服务
            -> 附件与文件 Adapter
            -> 审批 Adapter
            -> AI Provider Adapter
            -> 异步任务与补偿服务
            -> 审计服务
                -> MySQL
                -> Redis（缓存/幂等/短期任务状态）
                -> 消息队列或任务调度器
                -> 外部系统 / Mock
```

## 3. 技术栈原则

### 3.1 首选原则

优先复用公司 HR 主系统已经采用的：

- 前端框架和组件库。
- 后端语言、Web 框架和工程规范。
- 登录认证、用户组织、角色权限和数据范围组件。
- 数据库版本、缓存、消息队列、文件服务 SDK 和日志平台。
- CI/CD、配置中心、监控和部署模板。

合同系统不重复建设已有基础能力。

### 3.2 无法复用时的默认建议

- 前端：Vue 3 + TypeScript + 公司统一组件库。
- 后端：Spring Boot 3 + Java 17 或公司统一 Java 版本。
- 数据库：MySQL 8.x。
- 缓存：Redis。
- 异步任务：优先复用公司消息队列；没有统一组件时使用可靠任务表 + 定时调度器。
- API：REST/JSON，统一响应、错误码、分页、幂等头和审计上下文。
- 文件：只接统一文件服务，不自建对象存储。

以上是默认方案，不覆盖公司已有技术标准；正式开发前只需确认是否复用主系统，而不是重新讨论业务模型。

## 4. 后端工程结构

推荐按业务边界组织，而不是按“客户端/供应商端/AI 端”拆系统：

```text
backend/
  contract-api/                 API、DTO、参数校验、统一响应
  contract-domain/              合同聚合、状态机、领域规则
  contract-application/         用例编排、事务、权限和幂等
  contract-infrastructure/      数据库、缓存、任务、日志
  contract-integration/         外部 Adapter 和 Provider
    party/                      交易对方/HR/我方主体适配
    file/                       文件服务适配
    approval/                   审批适配
    ai/                         AI Provider 适配
    mock/                       Mock 实现
  contract-job/                 异步任务、轮询、回调和补偿
  contract-test/                集成测试、契约测试和测试数据
```

### 4.1 业务模块

- `contract-core`：合同主数据、生命周期和前置校验。
- `content-version`：正文、原始文本、版本和内容哈希。
- `contract-type`：合同大类、类型、子类型、字段配置和版本。
- `template`：模板、模板版本、变量映射和发布。
- `counterparty-reference`：交易对方引用、关系角色和快照。
- `attachment`：附件关联、业务分类、文件版本和权限。
- `ai-task`：解析、审查、结果版本、人工确认和任务审计。
- `approval`：外部审批实例、同步、锁定、撤回和转交。
- `performance-payment`：履行事项、收付款计划和履行记录。
- `permission-audit`：权限判定、敏感字段、临时授权和操作日志。

### 4.2 后端强制规则

- 业务状态、审批状态、AI 解析状态和 AI 审查状态分别校验和保存。
- 所有写操作支持幂等键和乐观锁。
- 所有外部回调先验签、校验业务对象、校验代次和幂等，再更新业务数据。
- 业务代码只依赖内部接口，不直接依赖 Dify、文件服务或审批系统 SDK 返回对象。
- 关键操作统一写审计：创建、编辑、版本、状态、审批、AI、文件、导出、授权和配置变更。

## 5. 前端工程结构

```text
frontend/
  src/
    app/                         路由、布局、登录态、全局异常
    pages/
      contract-workbench/        合同工作台
      contract-ledger/           合同台账
      contract-create/           合同创建/草稿编辑
      contract-detail/            合同详情
      approval-workbench/         审批工作台
      system-config/             分类、模板、连接、权限与审计
    modules/
      contract/                  合同表单、状态动作、列表组件
      counterparty/              交易对方选择和快照展示
      content-version/           正文版本组件
      attachment/                附件上传、预览和下载
      ai/                        AI 任务和结果确认
      approval/                  审批状态和历史
      performance/               履行与收付款
    api/                         只调用合同系统 API
    permissions/                 页面、按钮和字段展示控制
    shared/                      表格、表单、状态、错误和格式化组件
```

### 5.1 前端页面原则

- 前端只负责展示和交互，不能把隐藏按钮当作权限控制。
- 页面动作由后端返回的当前状态、权限和前置校验结果共同决定。
- 合同详情页承载 AI、审批、签署、履行、变更和附件动作，不新增重复导航。
- AI 和审批展示合同系统归一化后的数据，不直接展示第三方原始响应。
- 外部主体选择统一为“交易对方选择”，页面通过关系角色区分客户、供应商、合作方和员工。
- 先使用 Mock API 和固定数据完成页面交互，再切换真实 API。

## 6. API 分层

```text
页面 API
  -> 应用用例 API
      -> 领域规则
      -> 数据仓储
      -> 外部 Adapter
```

### 6.1 页面 API 示例

```text
POST   /api/contracts
GET    /api/contracts
GET    /api/contracts/{id}
PUT    /api/contracts/{id}/draft
POST   /api/contracts/{id}/content-versions
POST   /api/contracts/{id}/submit-approval
POST   /api/contracts/{id}/ai/extract
POST   /api/contracts/{id}/ai/review
POST   /api/contracts/{id}/attachments/upload-ticket
POST   /api/contracts/{id}/void
```

正式路径以公司 API 规范为准；这里表达资源和动作边界，不直接等同于最终接口文档。

### 6.2 统一请求上下文

每个请求至少包含：用户身份、组织上下文、请求 ID、幂等键（写操作）、客户端来源和接口版本。后端从登录态获取用户身份，不信任前端传入的操作者 ID。

### 6.3 统一错误分类

- `AUTH`：未登录或鉴权失败。
- `FORBIDDEN`：无数据、字段或动作权限。
- `VALIDATION`：字段或前置条件不满足。
- `CONFLICT`：版本冲突、状态冲突或重复操作。
- `DEPENDENCY`：外部系统不可用或返回异常。
- `TASK_FAILED`：AI、审批或文件任务失败。
- `INTERNAL`：系统内部异常。

## 7. 异步任务架构

统一任务字段包括：任务 ID、业务对象 ID、合同版本 ID、任务类型、Provider 任务 ID、状态、重试次数、幂等键、开始/结束时间、失败原因和结果版本。

```text
创建任务
  -> 入库 pending
  -> 提交 Provider
  -> polling / callback
  -> 校验结果
  -> 落库 success / waiting_confirm / failed
  -> 重试或人工补偿
```

- 合同保存不等待 AI、审批或文件任务完成。
- 轮询和回调都必须经过同一结果处理器。
- 旧合同版本的晚到结果不能覆盖新版本或人工确认结果。
- 重试必须有上限、退避和人工重发入口。
- 任务失败必须展示失败原因，不得默认成低风险、空数据或成功。

## 8. 前后端并行开发顺序

### 第一个业务切片：草稿闭环

后端同时完成：

- 合同创建 API。
- 合同类型和扩展字段读取。
- 草稿保存和查询。
- 合同台账查询。
- 合同详情查询。
- 权限过滤、乐观锁和审计。

前端同时完成：

- 合同台账页面。
- 合同创建表单。
- 草稿编辑和保存反馈。
- 合同详情基础布局。
- 状态标签和动作区域。

联调验收：

```text
选择合同类型
→ 填写通用和扩展字段
→ 保存草稿
→ 台账查询
→ 进入详情
→ 再次编辑
→ 记录审计
```

### 后续业务切片

1. 正文版本和文件附件。
2. AI 解析 Mock 和人工确认。
3. AI 审查 Mock 和法务确认。
4. 审批 Mock、回调、驳回、撤回和转交。
5. 待签署、签署文件和生效。
6. 履行事项、收付款和完成/终止。
7. 变更、补充协议、权限和商用加固。

每个切片都必须同时包含后端、前端、权限、审计、异常和测试，不只完成页面。

## 9. 部署环境

```text
本地开发：合同系统 + MySQL + Redis + Mock
测试环境：合同系统 + 测试数据库 + Mock/外部沙箱
预生产：合同系统 + 脱敏数据 + 外部沙箱联调
生产环境：合同系统 + 正式主数据/文件/审批/AI 服务
```

- 配置和密钥按环境隔离，密钥不得进入代码仓库。
- 外部连接配置支持启停、测试连接、超时和重试参数。
- 生产环境禁止使用测试 Provider 和测试文件空间。
- 监控至少覆盖 API 错误率、任务积压、外部调用耗时、回调失败、文件失败、AI 失败和权限拒绝。

## 10. 本方案待确认项

只确认技术环境，不重新确认一期业务范围：

1. 公司 HR 主系统使用的前后端技术栈和组件库。
2. 公司统一认证、用户组织、数据权限和审计组件。
3. MySQL、Redis、消息队列和任务调度的公司标准。
4. CI/CD、配置中心、日志、监控和部署平台。
5. 后端工程是独立仓库还是加入现有主系统工程。

若已有公司标准，直接复用；若没有，则按第 3.2 节默认方案落地。
