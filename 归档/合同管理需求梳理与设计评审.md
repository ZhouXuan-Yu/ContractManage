## 一、需求梳理（把对话整理清楚）

### 1. 项目定位
在人力资源产品线下，做一个**相对独立的合同管理系统**，管理企业对外签署的**商务合同**（服务 / 采购 / 销售合同）。这个项目的核心卖点不是"台账"，而是**两个 AI 能力**：合同智能解析 + 法律风险审查。

### 2. 核心能力（5 项业务 + 2 项支撑）

| # | 能力 | 一句话说明 | 落点表 |
|---|------|-----------|--------|
| 1 | 合同管理 | 合同台账 + 状态流转 + 变更/补充协议 | t_contract_main / t_contract_change |
| 2 | 合同生成 | 基于模板在线起草 | t_contract_template |
| 3 | 合同导入 | 上传 PDF/DOCX，留存原文 | t_contract_attachment |
| 4 | 合同解析 | AI 把合同解析成条款 / 标的 / 付款计划 | t_contract_clause / t_contract_subject / t_contract_payment_plan |
| 5 | 法律风险审查 | AI 中台"法律专家"判定法律风险 | t_contract_ai_review |
| 6 | 客户主体 | 预留接口，本地建表暂存（**非完整模块**） | t_contract_customer |
| 7 | 审计日志 | 操作可追溯 | t_contract_operate_log |

### 3. 关键澄清（你纠正过的点，我确认理解对了）
1. **不是每个名词都是一个模块**——上面 7 项里，"客户"是支撑数据不是模块，"审计"是公共能力不是业务模块。
2. **客户数据**：只留表 + 留接口（`external_customer_id` + `source_sync_status`），让合同流程能跑通即可；未来由**专门的客户管理系统**提供数据，通过接口回填，**不是**用你那个销售管理系统的导出数据。
3. **销售管理系统**：你之前做的是纯统计/导出，跟本项目无关。合同里的"产品 / 服务项"只是合同内容（标的），不是一个销售模块。
4. **招聘系统**：无关。
5. **员工劳动合同 ≠ 本项目**（⚠️ 这是我最想跟你确认的一点，见第五节问题 1）：HR 主系统 `emp_work_info` 里已经有劳动合同字段（员工跟公司签的劳动合同）；本项目是公司跟外部客户/供应商签的**商务合同**，是两回事。

## 二、项目边界

**在项目内**：合同台账、模板起草、文件导入、AI 解析、AI 法律审查、变更/补充协议、附件、客户主体表（预留）、审计日志。

**不在项目内**：
- 完整客户管理（CRM）——未来独立系统
- 销售管理（订单/商机/回款统计）——独立系统
- 招聘——独立系统
- 员工劳动合同——属于 HR 员工档案域，不混入本项目
- 审批流程引擎——一期可不接（字段已预留 `approval_no`）

## 四、数据库表设计评审

你设计的 10 张业务表（`t_contract_*`）+ 8 张复用公共表（`sys_*`）整体**结构和命名是对的**，方向正确。下面是具体评审意见。

### A. 命名规范对齐（⚠️ 重要）
公司目前**存在两套标准在打架**，你已正确选了主系统那套：

| 项 | 培训模块命名规范 | HR 主系统设计文档 | 你的合同表 |
|----|-----------------|------------------|-----------|
| 主键 | `表核心含义_id`（如 lecturer_id） | `id` | `id` ✓ |
| 主键生成 | 自增 | 雪花算法（非自增） | 雪花（非自增）✓ |
| 逻辑删除 | `is_deleted` | `deleted` | `deleted` ✓ |
| 表前缀 | `t_业务域_表含义` | 同 | `t_contract_*` ✓ |

**结论**：你已按《人力资源管理系统数据库设计文档》来，是对的。但要提醒：如果合同系统将来跟 HR 主系统同库部署，建议推动全公司**统一以主系统规范为准**，废弃培训模块那套"自增 + is_deleted + xxx_id 主键"，否则会出现风格不一致。

### B. 字段级修改建议

1. **`t_contract_clause.clause_type` 用 VARCHAR 违反枚举规范** ⚠️
   - 现状：`VARCHAR(32)` 存英文编码（payment/breach/delivery/...）
   - 规范："状态、类型字段统一 tinyint 数字枚举，禁用字符串"
   - 建议改为 `TINYINT`：1 付款、2 违约、3 交付、4 保密、5 争议解决、6 其他

2. **`t_contract_customer` 缺 `customer_type`** ⚠️
   - `customer_name` 注释写了"企业 / 个人主体名称"，但没有字段区分
   - 建议加 `customer_type TINYINT`：1 企业、2 个人

3. **`customer_id` 语义偏窄**（建议级别，可不改）
   - 采购合同场景下，对方是"供应商"不是"客户"
   - 两个选择：① 保留 `customer_id` 但注释明确为"交易对方主体（客户/供应商）"；② 改成 `counterparty_id`（交易对方）。一期建议选 ①，改动最小。

4. **缺索引设计** ⚠️（什么是索引：数据库表的"目录"，给经常查询/筛选的列建的快速查找入口；没索引就要全表逐行扫描，数据量大就慢）
   - 主系统规范要求每表明确列 `PRIMARY KEY / UNIQUE KEY / 二级索引`，你的表只有字段说明没写这一栏
   - 索引设计（补上这一栏即可）：

   | 表 | 索引类型 | 字段 | 为什么 |
   |----|---------|------|--------|
   | t_contract_main | UNIQUE | contract_no | 合同编号不能重复 |
   | t_contract_main | INDEX | customer_id | 按客户查合同 |
   | t_contract_main | INDEX | contract_status | 按状态筛选 |
   | t_contract_main | INDEX | contract_type | 按类型统计 |
   | t_contract_main | INDEX | sign_date | 按签订日期范围查 |
   | t_contract_clause | INDEX | contract_id | 查某合同的全部条款 |
   | t_contract_subject | INDEX | contract_id | 查某合同的全部标的 |
   | t_contract_payment_plan | INDEX | contract_id | 查某合同的付款计划 |
   | t_contract_ai_review | INDEX | contract_id, task_status | 查某合同审查记录、按任务状态轮询 |
   | t_contract_operate_log | INDEX | contract_id, operate_time | 按合同/时间查操作记录 |

5. **`origin_file_text` 建议从 TEXT 改为 MEDIUMTEXT** ⚠️
   - 完整合同原文可能超过 TEXT（64KB）上限
   - 建议 `MEDIUMTEXT`（16MB）更稳妥；同时保留附件表存文件本身（对象存储 URL）

### C. 结构建议（可选优化）

6. **金额字段已统一 DECIMAL(18,2)**：主表 `total_amount`、标的 `unit_price/subtotal_amount`、付款 `plan_amount` 一致 ✓

7. **`risk_items_json` 用 JSON 存风险明细，一期可接受**
   - 符合规范"扩展配置字段用 JSON 存储"
   - 但若后续要"按风险类型/等级做统计报表"，JSON 查询困难，届时再拆一张 `t_contract_risk_item` 表。一期先 JSON。

8. **审批字段预留正确**：`approval_no` 关联 `sys_approval_instance.approval_no`，一期留 NULL ✓

### D. 已正确设计的点（不用改）
- 主表 `our_role`（甲方/乙方）区分我方角色 ✓
- `source_type`（模板起草 / 文件导入）区分合同来源 ✓
- `is_ai_extract_finish` 记录 AI 解析状态 ✓
- `t_contract_ai_review.review_version` 支持多次审查 ✓
- 客户表 `external_customer_id + source_sync_status` 预留外部接口 ✓
- 审计日志 `before_json/after_json` 前后快照 ✓

## 五、客户数据测试方案

`t_contract_customer` 是本地表，**不依赖外部客户系统就能测通合同全流程**，两条路径：

- **路径 A（本系统录入）**：手动建客户 → `source_sync_status = 0`、`external_customer_id = NULL`。合同「创建 → 导入 → 解析 → 审查」全程不碰外部系统。
- **路径 B（模拟外部同步）**：先与客户系统**约定接口契约**（同步入参/出参字段），用 mock 脚本模拟推送，验证 `source_sync_status = 1` 与 `external_customer_id` 回填逻辑。

测试准备：① 种子数据（若干测试客户 + 几份合同样例，覆盖服务/采购/销售）；② 客户同步接口契约（字段、触发方式、幂等规则）。
